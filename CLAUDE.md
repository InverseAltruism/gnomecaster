# Gnomecaster

In-game AI helper for World of Warcraft. The player types into an addon panel; a desktop companion app answers with text and actions: waypoints, the quest arrow, raid marks, macros, action bar placement, key bindings, an allowlist of console variables, and explanations of recent Lua errors.

The code started as the Wowpilot prototype, imported and renamed to Gnomecaster on 2026-10-16 (see `docs/PROGRESS.md`). The old name survives only in that history, in the README's upgrade note, and in `.gitignore` (the archive's file name). Slash commands are `/gc` and `/gnomecaster`; the beacon magic is `"GC"`; environment variables are `GNOMECASTER_*`.

Known defects and the quality backlog are in `docs/REVIEW.md`; the current refinement plan is `docs/PLAN.md`.

## Layout

- `addon/Gnomecaster/`: the addon (Lua 5.1, WoW API). Load order is the TOC: Core, Json, Errors, Places, Context, Beacon, Inbox, Actions, UI, Request. `Places` finds a place by name in the game's own map data (entrances, delves, world quests and bosses, flight points, area POIs, zones, the quest log) within 80 maps and 30 ms. `ack.ttf` is an empty file the companion fills while it answers.
- `addon/Gnomecaster_Inbox01` to `20`: load-on-demand reply slots, generated by `tools/make_inboxes.py`. Do not edit them by hand.
- `companion/gnomecaster_companion.py`: the entry script; the code is the `companion/gnomecaster/` package (Python 3.10+, Pillow pinned in `companion/requirements.txt`): `protocol` (screenshot decoding), `slots` (reply files, ready and ack signals), `model` (OpenAI-compatible client: one deadline per question, errors in plain words, OpenRouter web search), `prompt` (system prompt, reply parsing, sanitizing), `conversation` (the last 10 exchanges per conversation key), `transcript` (every exchange as JSON lines, 14 days), `demo` (offline answers when no model is set up), `brain`, `config` (settings file and provider presets), `game` (game folder, install), `serve` (request loop), `cli`.
- The desktop app (Windows first): `companion/gnomecaster_app.py` is its entry; in the package, `service` (the request loop in a thread, reporting each question and answer), `app_api` (the calls the window makes), `app` (pywebview window, pystray tray icon, close to tray, single instance, logs), `oauth` (Sign in with OpenRouter, PKCE), `winsys` (registry, autostart, folders). `desktop/ui/` is the window: `api.js` is the contract with `app_api.Api` (its mock backend serves `?mock=` in a browser), `app.js` the screens.
- `packaging/`: the Windows build. `gnomecaster.spec` (PyInstaller), `gnomecaster.iss` (Inno Setup installer), `requirements-*.in` (exact pins) locked into hash-checked `requirements-*.txt` by `lock.py`, `check_bootloader.py`. `.github/workflows/windows.yml` builds, tests and smoke-tests it; `packaging/README.md` explains the order.
- `assets/brand/`: `gnomecaster-icon.svg` and `installer-side.svg` are the sources; every icon and installer image is generated from them by `tools/make_icons.py`.
- `tests/`: `run_all.sh` runs the Lua scenarios (real addon code on a mocked WoW API, `wowmock.lua` with `wowmock_templates.lua` for Blizzard's frame templates and `wowmock_places.lua` for a small game world; scenarios in `run_tests.lua`, `run_places.lua`, `run_beacon.lua`, with `beacon_matrix.py` rendering plates under gamma and brightness; the real companion through `driver.py`; fake screenshots from `render.py`) and the Python unit tests (`test_*.py`).
- `tools/`: `make_inboxes.py` (reply slots), `wow_api.py` (checks every WoW API call against Blizzard's UI source), `eval_models.py` with `eval_scenarios.py` and `eval_apply.lua` (scores real models on real requests).

## How the two halves talk

Addons cannot use the network or write files during play, so both directions go through the file system.

- Addon to companion (`Beacon.lua`): the request JSON is packed as `"GC"`, protocol byte, 2-byte length, adler32, payload. It is drawn as a grid 96 cells wide, 3 px per cell, 3 bits per cell, for two frames, then `Screenshot()` is called. Two styles (`/gc beacon`): `dim` (default) is a plate at 0.08/0.45 intensity with a gold frame and caption outside the cells, placed by `UI.BeaconAnchor(w, h)` beside the panel; `classic` is the original full-intensity square in the top-left corner, the only style proven in game. The decoder searches the whole screenshot and sets its per-channel thresholds from the marker row, so either style and the game's gamma and brightness are read the same way; the dim style needs PNG (the addon forces it). The companion watches `Screenshots/`, decodes new files, and deletes only those that contain a beacon, after their reply is written. The payload limit is 2400 bytes; `Request.lua` drops context detail over 7 levels until it fits. Packets carry `conv` (conversation key, kept in SavedVariables, renewed by `/gc new`) and `last` (at most 6 results of the previous reply's actions).
- Companion to addon (`Inbox.lua`): the companion writes `GnomecasterInbox({...})` into `inbox.lua` of every slot from the requested one up to 20. The addon calls `LoadAddOn` on the next unused slot and skips slots that are already loaded. Each slot loads once per UI session (proven in game 2026-10-17). Whether `/reload` frees them is unverified (`docs/REVIEW.md`, R4); `/gc status` shows the next slot. The Reload warning comes at `Inbox.LowMark()` slots left (3 with a working ready signal, 6 without). Blizzard's AddOns list cannot hide or collapse `## Group` children, so every slot is a visible line: keep the count low. Replies carry `sid` (per UI load) and `rid` (per request) and are ignored when either does not match.
- Signals (experimental): `EditBox:SetFont()` reports whether a font file is valid, so the addon can read files without spending a slot. `ready.ttf` in the next 9 slots says a reply is written; `Gnomecaster/ack.ttf` says the companion picked the question up. A signal counts only after it was seen going from empty to filled; otherwise the addon falls back to timed polling.

## The window and the backend

pywebview hands the page every public method of `app_api.Api` (including `getHistory`, the transcripts, and `openTranscripts`) and, recursively, of its public attributes; JavaScript can also reach underscore names by path. So: only the window's calls are public, all state is underscore-prefixed, no call takes a path or URL from the page, and none returns the API key (`tests/test_app.py` checks the public surface against `api.js` and that `getState` never contains the key). Each call takes one dict, returns JSON and never raises.

## Trust boundary

Model output is untrusted, and so are search results, game strings in the context, `last` results and transcripts shown in the window (always as text, never as HTML). The companion's `sanitize()` keeps only known action types and scalar fields, strips markdown citation links from `say`, and `lua_value()` escapes everything it writes into Lua. Transcripts pass through `model.redact`, so the API key never reaches them or `getHistory`. The addon re-checks every action in `Actions.lua`: macro bodies may only use the commands in `MACRO_COMMANDS` (no `/run`, `/script`, `/click` or chat), settings only the names in `CVAR_ALLOW`, numbers must be integers where the game expects them, and model text is escaped before display (`ns.Escape`). The companion reads `MACRO_COMMANDS` and `CVAR_ALLOW` from `Actions.lua` for its prompt, so those tables are the single source. A `goto` names a place; the addon resolves it from game data and never takes coordinates from the model for it. Navigation and marks run at once (a mark asks first if the target changed since the question); macro, bar, bind and setting changes wait for Apply unless `/gc auto on`, and a binding that would replace an existing one always asks.

## Constants mirrored across Lua and Python

`tests/test_contract.py` compares them; a change on one side fails it until the other follows.

| Constant | Lua side | Python side |
|---|---|---|
| reply slot count (20) | `Core.lua` `ns.NUM_SLOTS` | `protocol.NUM_SLOTS`, `tools/make_inboxes.py` |
| protocol version, magic | `Core.lua` `ns.PROTOCOL`, `Beacon.lua` `MAGIC` | `protocol.PROTOCOL`, `protocol.MAGIC` |
| grid width, marker colours | `Beacon.lua` `GRID_W`, `MARKER` | `protocol.GRID_W`, `protocol.MARKER` |
| action types | `Actions.lua` `handlers` | `prompt.ACTION_TYPES` |
| timed polls vs signalled slots | `Inbox.lua` `BLIND` | `slots.PROBE_AHEAD` (must exceed the poll count) |
| TOC Interface list | `Gnomecaster.toc` | `tools/make_inboxes.py` |
| version | `Gnomecaster.toc` `## Version` | `gnomecaster.__version__` (also read by the PyInstaller spec and the installer build) |
| installer's running-app check | `packaging/gnomecaster.iss` `#define AppMutex` | `app.MUTEX`, held through `winsys.claim_instance` (`tests/test_app.py`) |

After changing the slot count or the Interface list, run `python3 tools/make_inboxes.py`; the contract test also compares the committed slots with the generator.

## Checks before handing anything over

Needs a Lua 5.1 interpreter (WoW runs Lua 5.1), python3 and Pillow. This server has no Lua package; build 5.1.5 in a scratch directory from https://www.lua.org/ftp/lua-5.1.5.tar.gz (sha256 `2640fc56a795f29d28ef15e13c34a47e223960b0240e8cb0a82d9b0738695333`, `make posix`).

    LUA=/path/to/lua TMPDIR=/path/to/scratch bash tests/run_all.sh     # exits non-zero on any failure
    LUA=/path/to/lua python3 tools/wow_api.py check                     # every WoW API call verified
    GNOMECASTER_API_KEY=... LUA=/path/to/lua python3 tools/eval_models.py --model openai/gpt-6-luna
    python3 tools/make_icons.py --check                                 # generated images match their SVGs (needs resvg 0.48.1)
    python3 packaging/lock.py --check                                   # hash locks match the pins, pins past the 14-day cooldown

- Every Python text file access names `encoding="utf-8"`: Windows reads text as cp1252 otherwise (the 1.2.0 build failed on it). `run_all.sh` sets `PYTHONWARNDEFAULTENCODING=1` and `PYTHONWARNINGS=error::EncodingWarning`, so a missing encoding fails on Linux too, in the tests and in the companion they start.
- The mock rejects widget methods that Blizzard does not document (`tests/wow_api_methods.lua`, regenerated with `tools/wow_api.py mock-methods`). Any new WoW call must pass `wow_api.py check`; nothing here can run the game client.
- The window: serve `desktop/ui/` and open `index.html?mock=fresh` (or `busy`, `aiproblem`, `live`, `nogame`) in a browser; screenshot both colour schemes. The real backend can be driven the same way by forwarding the page's `window.pywebview.api` calls to `app_api.Api` over HTTP.
- Releases are built on GitHub's Windows runners (`windows.yml`). For testing by hand, this server has a Windows 11 VM (`~/vm/win11`, see its README): off unless started, isolated network, and `build.ps1` there builds the installer offline from a copy of this source. Run installers and the app in it with `vm.py desktop`, not `vm.py ssh`, and stop it afterwards.
- `eval_models.py` spends real money (about $0.0002 per scenario on the cheap models). Results go to `--out`; keep raw results out of the repo.

## Game constraints the code relies on

- Lua 5.1 only: no `goto`, no `//`, no integer subtype.
- Nothing runs in combat. Macro, bar and binding APIs are protected there, and Midnight (12.x) returns secret values that addon code may not compare or do arithmetic on. Every value sent out goes through `ns.Plain` or `ns.IsSecret`.
- Each `Context.Collect` section runs under pcall, so an API missing on one game flavor cannot break a request.
- Proven on a real client (2026-10-17): the classic beacon is decoded, load-on-demand files are re-read from disk mid-session. Not yet proven: the dim plate, the template-based panel, place lookups on live data, the `SetFont` signals, and what `/reload` does to loaded slots. The test in `README.md` covers these.
